# C. 영업 지원 봇 (c-sales-brief)

## 목적

알에스팀은 대부분 B2B 영업(랜딩페이지 + 영업 포트폴리오 제시)으로 고객을 만납니다. 이 봇은 **영업 준비 시간을 줄이고 미팅 성사율을 높이는 것**이 목표입니다.
대상 이름·홈페이지·메모를 넣으면 미팅 전에 읽을 브리프와 한 장짜리 제안서 초안을 만들고, 영업 담당자가 검토합니다.
**이 봇은 아무것도 발송하지 않습니다.** 승인된 제안서는 영업 담당자가 고쳐서 직접 전달합니다.

## 흐름

```
대상 입력(이름·URL·업종·메모)
  → (URL 있으면) 그 페이지 1개만 조회 → 태그 제거한 평문(최대 6000자)
  → LLM: 우리 서비스(samples/offering.json) + 대상 정보 → 브리프 JSON
  → 검증(필수 필드) → data/c-sales-brief/briefs/<slug>.md 저장
  → 승인 대기열(kind: sales-proposal) 제출
  → 영업 담당자: review / show → approve 또는 reject
  → 승인 건으로 미팅이 잡히면 meeting 기록 (효과 지표)
```

## 명령어

> `pnpm c:sales` 는 pnpm 내장 명령 `pnpm config` 의 별칭과 겹쳐 동작하지 않습니다. **`pnpm c:sales`** 로 실행하세요.

```bash
pnpm c:sales help
pnpm c:sales brief --name "이디야커피" --url https://www.ediya.com --industry "커피 프랜차이즈" --notes "가맹점 단골 관리 검토"
pnpm c:sales brief --name "동네 베이커리" --notes "종이 스탬프 분실이 잦음"      # URL 없이 메모만
pnpm c:sales brief --file src/prototypes/c-sales-brief/samples/targets.json      # 여러 대상 일괄
pnpm c:sales review [--all]
pnpm c:sales show <id>
pnpm c:sales approve <id> [--note "메모"]
pnpm c:sales reject <id> [--note "사유"]
pnpm c:sales meeting <id>        # 승인된 항목만, 항목당 1회
```

오류가 나면 종료 코드 1을 돌려줍니다. 일괄 처리에서는 한 대상이 실패해도 나머지는 계속 만들고, 마지막에 실패 건수와 함께 1로 끝납니다.

## 파일

| 파일 | 내용 |
|---|---|
| `cli.ts` | 명령줄 진입점 (`node:util` parseArgs) |
| `brief.ts` | 브리프 생성·검증·마크다운 렌더링, 승인/반려/미팅 기록 |
| `fetcher.ts` | `PageFetcher` 인터페이스, `HttpPageFetcher`(10초 제한·식별 User-Agent·1페이지), `htmlToText` |
| `samples/offering.json` | 우리 서비스·포트폴리오 **(임시 데이터 — 실제 내용으로 교체 필요)** |
| `samples/targets.json` | 일괄 처리 예시 대상 3곳 (1곳은 공개 홈페이지, 2곳은 가상의 메모 전용) |
| `prompts/c-sales-brief-generate.md` | 브리프 생성 프롬프트 |
| `tests/c-sales-brief.test.ts` | mock LLM·가짜 수집기 테스트 |

생성 파일:

- `data/c-sales-brief/briefs/<slug>.md` — 브리프 (같은 이름이면 `-2`, `-3`을 붙여 덮어쓰지 않음)
- `data/approvals.json` — 승인 대기열 (meta: `slug`, `target`, `url`, `file`)
- `data/metrics.jsonl` — `generated`(소요 시간 포함) / `failed` / `approved` / `rejected` / `meeting_booked`

브리프 섹션: 대상 요약 · 확인된 사실 · 추정(검증 필요) · 예상 고민 · 제안 각도 · 추천 서비스 · 제안서 초안 · 미팅 질문 · 수집 정보 출처/실패 사유

## 사실/추정 분리 설계

영업 제안서에서 가장 위험한 것은 **모델이 지어낸 사실을 영업 담당자가 그대로 말하는 것**입니다.

1. LLM 출력 JSON에서 `facts`(입력에 적힌 것만)와 `assumptions`(“추정: ”으로 시작)를 다른 필드로 강제하고, 브리프에서도 다른 섹션으로 나눕니다.
2. 프롬프트가 입력에 없는 숫자·고객사·연혁·수상 이력과, offering.json 에 없는 우리 실적을 만들지 말라고 명시합니다. 기대 효과에 수치 약속을 금지합니다.
3. 모르는 연락처·담당자는 `[담당자명]` 같은 빈칸으로 둡니다.
4. “수집 정보 출처/실패 사유” 섹션에 무엇을 근거로 썼는지(URL, 수집 성공/실패, 글자 수, 메모)를 남겨 검토자가 바로 대조할 수 있게 합니다.
5. 수집 실패는 예외가 아니라 결과값이라 메모만으로 계속 만들고, 실패 사유를 프롬프트와 브리프 양쪽에 적습니다.

검증은 필드 존재·타입만 합니다. **facts 가 실제로 페이지에 있는지 자동 대조하지는 않습니다** (다음 단계 참고).

## 지표

| 기준 | 지표 | 기록 방식 |
|---|---|---|
| 자동화 | 브리프 생성 수, 1건 준비 시간(`generated.durationMs`: 수집+LLM), 실패율 | `metrics.track` |
| 효과 | 승인율(제안서가 그대로 쓸 만한가), **미팅 성사율 = meeting_booked / approved** | `approve`·`meeting` 명령 |
| 유지보수 | `failed` 비율·원인(JSON 깨짐, 필드 누락), 프롬프트·offering 파일만 고치면 되는 구조 | `failed.meta.error` |

“준비 시간 단축”의 실제 효과는 기존 수작업 준비 시간(사람이 재야 함)과 비교해야 알 수 있습니다. 지금은 봇 쪽 시간만 기록합니다.

## 한계

- **크롤링 범위**: 입력한 URL 1페이지만, 서버가 내려준 HTML만 읽습니다. 자바스크립트로 그리는 사이트(예: 확인 시점의 kyochon.com)는 “읽을 글자 없음”으로 실패 처리됩니다. 하위 페이지·뉴스·SNS는 보지 않습니다. 사이트 이용약관·robots.txt 검토는 아직 안 했습니다(사람이 링크를 여는 것과 같은 수준의 단발 조회만 함).
- **정확도**: 페이지에 남아 있는 오래된 공지도 “현재 사실”로 읽습니다(아래 Verdict 참고). facts 자동 대조가 없어서 사람 검토가 필수입니다.
- **개인정보**: 페이지에 담당자 이름·연락처가 있으면 브리프에 들어갈 수 있습니다. 이 프로토타입은 공개 기업 정보만 넣는 것을 전제로 하며, 개인 사업자의 개인 연락처를 수집·보관하는 용도로 쓰면 안 됩니다. 브리프 파일은 `data/`(git 제외)에만 저장됩니다.
- **우리 정보가 임시값**: offering.json 의 포트폴리오 결과가 placeholder 라 제안서의 근거가 약합니다. 실제 사례를 넣어야 설득력이 생깁니다.
- 로컬 모델이 느립니다(실측 약 3분/건).

## 다음 단계

2. facts 각 항목을 수집 본문·메모와 문자열 대조해 근거 없는 항목에 ⚠ 표시.
3. 공지·팝업처럼 날짜가 있는 문장은 “게시 시점 불명”으로 표시하도록 프롬프트 보강.
4. 실제 영업 2~3주 운영해 준비 시간(사람) 전/후와 미팅 성사율 비교.
5. D(커뮤니티 모니터링)의 사장님 고민 키워드를 예상 고민 입력으로 받는 규약(shared handoff) 검토.

**What worked**
- 첫 시도에 JSON 파싱·필드 검증 통과 (프롬프트 수정·재시도 없음).
- 사실 7개를 수집 본문과 직접 대조했고 **7개 모두 페이지나 메모에 근거가 있었습니다**. 매출·매장 수·고객사 같은 지어낸 숫자는 없었습니다. 추측은 모두 “추정: ”으로 분리됐습니다.
- 제안서 초안은 존댓말, `[담당자명]` 빈칸, 수치 약속 없음, 15~20분 미팅 제안으로 끝나 영업 담당자가 손보기 좋은 수준입니다. 미팅 질문 5개도 추정을 확인하는 질문이었습니다.
- 수집 실패 경로(타임아웃, JS 렌더링 페이지)가 실제 사이트에서도 크래시 없이 실패 사유로 남았습니다(사전 수집 점검: gongcha.co.kr 10초 초과, kyochon.com 본문 없음).

**What didn't**
- 건당 약 3분 — 다른 에이전트와 공유 중인 로컬 모델이라 느렸습니다. 사람이 조사하는 시간보다는 짧겠지만 대화형으로 쓰기엔 깁니다.
- 제안 각도가 페이지의 공지 하나(“이디야멤버스 리뉴얼 준비로 서비스 점검… 5월15일”)에 크게 기댑니다. 실행 시점은 11월이라 **오래된 공지일 가능성이 높은데** “리뉴얼 준비 소식을 확인하였습니다”라고 현재 일처럼 썼습니다. 사실 자체는 맞지만 해석이 틀릴 수 있습니다.
- 우리 포트폴리오가 placeholder 라 제안서가 “일반적인 쿠핀 ON 소개” 수준에 머뭅니다.
- 대형 프랜차이즈 본사에 매장용 쿠폰 서비스를 붙이는 제안 자체의 적합성(이미 자체 멤버십·쿠폰 B2B 운영 중)은 모델이 따지지 않았습니다. 추천 서비스는 사람이 판단해야 합니다.

**Surprises**
- `pnpm c:sales` 가 pnpm 내장 `config` 별칭으로 가로채져 실행되지 않습니다 (`pnpm c:sales` 필요). 루트 README 표의 `pnpm c:sales` 도 같은 문제입니다.
- 처음 User-Agent 에 한글을 넣었더니 Node fetch 가 헤더 오류(ByteString)로 모든 수집에 실패했습니다. ASCII 로 바꿔 해결했습니다.

**Recommendation**
사실/추정 분리와 “지어내지 않기”는 기대보다 잘 지켜져 **영업 준비 초안 도구로는 쓸 만합니다.** 다만 1건 실행이라 정확도 결론은 이르고, 효과(미팅 성사율)는 아직 측정하지 못했습니다. 다음은 offering.json 을 실제 포트폴리오로 바꾼 뒤 실제 영업 대상 5~10곳에 써서 영업 담당자의 수정량·준비 시간·미팅 성사율을 재는 것입니다. 오래된 공지 문제는 다음 단계 3번(날짜 있는 문장 표시)으로 대응합니다.

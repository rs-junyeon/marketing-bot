# A. 사장님 대상 콘텐츠 자동화 (`a-content`)

## 목적

동네 매장 사장님이 실제로 고민하는 주제(단골 만들기, 비수기 매출, 리뷰 관리, 쿠폰 활용 등)로 **장사 정보 블로그 글**을 LLM이 초안으로 쓰고, 사람이 승인한 글만 발행합니다. 글 끝에는 코드가 UTM 링크가 붙은 서비스 소개(CTA)를 붙여서 **어떤 글이 랜딩 유입을 만들었는지** 측정할 수 있게 합니다.

검증하려는 가설: *"로컬 LLM만으로도 사람이 조금만 손보면 발행할 수 있는 품질의 사장님 대상 정보 글을, 승인 1번으로 꾸준히 만들 수 있다."*

## 흐름

```
 [D 모니터링] ──latest-topics.json──┐
                                    ▼
 samples/topics.json ──(없을 때)──▶ topics ──▶ draft ──▶ LLM (prompts/a-content-draft.md)
                                                │          │ JSON {title, body, summary}
                                                │          ▼
                                                │      검증(제목·길이·빈칸 표시) ──실패──▶ metrics: failed
                                                │          │ 통과
                                                │          ▼
                                                │      CTA + UTM 링크 붙이기, 수치·인용 경고 표시
                                                ▼          ▼
                                      drafts/<id>.md   승인 대기열(kind: blog-post)  ── metrics: generated
                                                           │
                                       review / show ──────┤
                                                           ├── reject ──▶ metrics: rejected
                                                           └── approve ─▶ channel.send(blog, dry-run)
                                                                          published/<slug>.md
                                                                          metrics: approved, sent
```

## 명령어

```bash
pnpm a:content topics                              # 글감 후보 (D 전달 주제 우선, 없으면 샘플)
pnpm a:content draft                               # 첫 번째 주제로 1건 생성
pnpm a:content draft --topic "비수기 매출" --count 2 # 주제 지정(목록에 없어도 됨), 여러 건
pnpm a:content review                              # 승인 대기 목록
pnpm a:content show <id>                           # 초안 보기 (승인 id 또는 draft id)
pnpm a:content approve <id> [--note "메모"]         # 승인 → 블로그 발행(dry-run)
pnpm a:content reject <id> [--note "사유"]          # 반려
```

브랜드 정보(서비스명·한 줄 소개·랜딩 URL·말투)는 `samples/brand.json`, 프롬프트 문구는 `prompts/a-content-draft.md` 에서 코드 수정 없이 바꿀 수 있습니다.

## 생성되는 파일

| 경로 | 내용 |
|---|---|
| `data/a-content/drafts/<draftId>.md` | 초안 (요약·주제·slug·승인 id·검토 경고 + 본문) |
| `data/a-content/published/<slug>.md` | 승인되어 발행(dry-run)된 글 |
| `data/approvals.json` | 승인 대기열 (공용) |
| `data/outbox.jsonl` | 발행 기록 (공용, dry-run) |
| `data/metrics.jsonl` | 지표 이벤트 (공용) |

## 측정 지표

| 관점 | 지표 | 어디서 |
|---|---|---|
| 자동화 | 생성 건수, 평균 생성 시간 | `generated` + `durationMs` |
| 자동화 | 승인율 (사람이 고치지 않고 통과한 비율) | `approved / (approved + rejected)` |
| 효과 | 발행 건수 | `sent` |
| 효과 | 글별 랜딩 유입 | `utm_campaign=<slug>` (랜딩 분석 도구에서 확인, 이 저장소에서는 아직 미수집) |
| 유지보수 | 생성 실패율 (JSON 깨짐·짧은 글·빈칸 표시) | `failed / (generated + failed)`, 실패 사유는 `meta.error` |

`pnpm report` 로 다른 프로토타입과 같은 표에서 비교됩니다.

## 한계와 다음 단계

- **사실 검증은 사람 몫입니다.** 프롬프트로 지어낸 통계·인용을 금지하고 `%`·"조사에 따르면" 같은 표현에는 경고를 띄우지만, "대부분 5분 안팎에서 갈립니다" 같은 근거 없는 단정은 잡지 못합니다.
- **맞춤법 오타가 남습니다.** 실행 결과에 "손문이"(손님이), "결재"(결제) 같은 오타가 있었습니다. 승인 전에 맞춤법 검사기를 한 번 거치게 하거나 LLM 교정 단계를 추가할 만합니다.
- **승인 화면이 CLI뿐입니다.** 승인 전 수정(edit) 기능이 없어서 고치려면 반려 후 다시 생성해야 합니다. 다음 단계: 초안 파일을 고치면 그 내용으로 발행하는 `edit` 흐름.
- **발행은 dry-run만 있습니다.** 실제 블로그(네이버 블로그·티스토리·자체 CMS) 채널은 `OutboundChannel` 구현으로 붙여야 합니다.
- **유입 측정이 끊겨 있습니다.** UTM 링크까지는 만들지만 랜딩 쪽 유입을 `lead_captured` 로 연결하는 부분은 B(랜딩) 또는 분석 도구 연동이 필요합니다.
- **같은 주제 중복 관리가 없습니다.** 이미 발행한 주제를 다시 쓰지 않게 하는 이력 체크가 필요합니다.
- 슬러그는 한글 제목 대신 `post-<날짜>-<짧은 id>` 형식입니다. 검색 노출용 영문 슬러그가 필요하면 별도 생성이 필요합니다.

### What worked
- JSON 출력 형식을 한 번에 지켰고 존댓말·실무 팁 구조(질문형 메뉴 안내, 주문 후 한마디, 방문 메모 등)가 사장님이 바로 써먹을 만한 수준이었습니다.
- 지어낸 통계·퍼센트·가짜 인용은 나오지 않았고, 본문에 서비스 홍보도 넣지 않았습니다(CTA는 코드가 붙임).
- 승인 → dry-run 발행 → 지표 기록까지 공용 모듈만으로 끝까지 이어졌습니다. 이미 처리한 항목을 다시 승인하면 에러로 막힙니다.

### What didn't
- 오타 2건("손문이", "결재 후")과 어색한 표현("나를 무시당했다")이 있어 **그대로 발행하기엔 부족하고 사람 교정이 필요**합니다.
- "대부분 첫 방문 중 5분 안팎의 경험에서 갈립니다", "강한 충성심을 보입니다"처럼 근거 없는 단정이 있었고, 현재 경고 규칙(`%`, "조사에 따르면")으로는 잡히지 않았습니다.
- 방문 메모 예시에 "남자, 30대" 같은 인상착의 기록을 권하는 부분이 있어 개인정보 측면에서 검토가 필요합니다.

### Surprises
- 한 건에 2분 30초가 걸렸습니다(모델 공유 상태). 하루 몇 건 수준의 배치 작업에는 충분하지만 대화형으로 쓰기엔 느립니다.
- 오히려 버그는 코드 쪽 CTA에서 나왔습니다. "쿠핀 ON**는**"처럼 서비스명 받침에 따라 조사가 틀려서, 조사 없는 "이름 — 설명" 형식으로 고쳤습니다(실행 결과 글에는 수정 전 문구가 남아 있음).

### Recommendation
파이프라인(주제 → 초안 → 승인 → 발행 → 지표)은 그대로 가져갈 만합니다. 다음은 ① 승인 전 수정(edit) 흐름, ② 맞춤법·근거 없는 단정 표현 교정 단계, ③ 실제 블로그 채널 연결과 UTM 유입 → `lead_captured` 연결 순서로 진행하길 권합니다. 품질 판단은 1건 표본이라 확정적이지 않으니, 주제 6개로 몇 건 더 만들어 승인율을 본 뒤 결정하는 것이 좋습니다.

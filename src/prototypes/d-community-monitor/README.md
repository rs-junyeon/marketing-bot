# D. 커뮤니티·트렌드 모니터링 (`d-community-monitor`)

## 목적

사장님(소상공인·자영업자)이 요즘 무엇을 고민하는지를 **공개 소스**에서 모아 키워드·고민·트렌드로 정리하고,
그 결과를 A(콘텐츠 자동화)의 글감과 C(영업 지원)의 대화 포인트로 넘긴다.
**이 프로토타입은 수집과 분석만 한다. 어떤 커뮤니티에도 글·댓글을 올리지 않는다.**

## 흐름

```
samples/sources.json ──collect──▶ data/d-community-monitor/items.jsonl (링크·제목 기준 중복 제거)
                                          │
                                       analyze  ① 코드로 키워드 집계 (토크나이저 + 불용어 + 관심 키워드)
                                          │     ② LLM(JSON)으로 테마·고민·콘텐츠 아이디어·영업 포인트
                                          │     ③ 근거 글 번호가 없는 항목은 코드가 버림
                                          ▼
     reports/<YYYY-MM-DD>.md / .json   latest-topics.json (→ A)   latest-sales-angles.json (→ C)
```

- LLM에는 글을 `[번호]`로 주고, 근거는 **글 번호로만** 받는다. 제목·링크는 코드가 번호로 다시 붙이므로 LLM이 링크나 기사 제목을 지어낼 수 없다. 범위 밖 번호·빈 근거 항목은 버리고 리포트에 개수를 남긴다.
- 샘플 글은 프롬프트에 `(샘플)`로 표시하고, 샘플만 근거인 항목은 리포트에 `[샘플 근거만]`, 전달 파일 reason에 `⚠ 샘플 데이터만 근거` 문구를 붙인다.

## 명령어

```bash
pnpm d:monitor collect               # 소스 수집 (소스별 가져옴/새 글/중복 건수 출력, 실패 소스는 건너뜀)
pnpm d:monitor analyze [--days 7]    # 최근 N일 글 분석 → 리포트·전달 파일 (로컬 Ollama 기준 수 분 걸림)
pnpm d:monitor report                # 최근 리포트 경로·요약
```

잘못된 명령, 최근 글 없음, LLM JSON 오류, 모든 소스 실패 시 종료 코드 1.

## 수집 소스와 약관·법적 고려

| 소스 | 형식 | 비고 |
|---|---|---|
| Google 뉴스 RSS 검색 4개 (`소상공인 단골`, `자영업자 쿠폰`, `사장님 리뷰 관리`, `소상공인 마케팅 AI`, 각 `when:7d`) | `rss` | 공개 RSS. 10초 타임아웃, 식별 가능한 User-Agent, 소스당 최대 30건 |
| `samples/community-sample.json` | `sample-file` | **직접 작성한 가상 글 10건** (`sample: true`). 실제 카페 글 아님 |

- **로그인이 필요한 네이버 카페(예: '아프니까 사장이다')는 크롤링하지 않는다.** 회원 전용 게시판 수집은 네이버 이용약관 위반이며, 게시글 무단 복제는 저작권·개인정보 문제도 생긴다. 샘플 파일은 "카페에서 이런 글을 볼 수 있다면"을 흉내 낸 것일 뿐이다.
- Google 뉴스 RSS 피드 자체에도 *"personal, non-commercial use"* 문구가 있다(실제 응답의 `<copyright>`). 사내 리서치용 프로토타입에서는 괜찮아도, **상용 서비스로 돌리려면 정식 뉴스 API(네이버 검색 API 뉴스, 빅카인즈 등)로 바꿔야 한다.**
- 실제 커뮤니티 연동은 공식 API·제휴(예: 카페 운영진 제휴, 배민외식업광장 같은 포털과의 협약)가 있어야 한다. 원문 저장 대신 제목·짧은 요약·링크만 남기는 현재 방식을 유지한다.
- 새 소스를 넣을 때는 `samples/sources.json`에 `{ "name", "type": "rss", "url" }`만 추가하면 된다. 관심 키워드는 `samples/keywords.json`.

## 생성 파일 (`data/d-community-monitor/`)

| 파일 | 내용 |
|---|---|
| `items.jsonl` | 수집 글 `{id, sourceName, title, link, publishedAt, collectedAt, snippet, isSample}` |
| `reports/<날짜>.md` | 상위 키워드 표, 관심 키워드, 테마, 고민, 콘텐츠 아이디어, 영업 포인트, 소스별 글 목록, 샘플 안내 |
| `reports/<날짜>.json` | 같은 내용의 구조화 데이터 (`pnpm d:monitor report`가 읽음) |
| `latest-topics.json` | A용 `TopicHandoff` (`shared/handoff.ts`의 `writeTopicHandoff`) |
| `latest-sales-angles.json` | C용 영업 포인트 `{generatedAt, angles[{text, sourceLinks}]}` (공용 규약 없음 → D 폴더 임시 파일) |

## A·C로의 전달

- **A**: `readTopicHandoff(store)`로 읽는다. `topics[]` = 콘텐츠 아이디어 `{title, reason, sourceLinks}`. 샘플만 근거인 주제는 reason 끝에 경고가 붙어 있으니 A가 걸러 쓸 수 있다.
- **C**: `data/d-community-monitor/latest-sales-angles.json`을 직접 읽어야 한다. 공용 규약이 필요하면 `shared/handoff.ts`에 추가를 요청한다(아래 "다음 단계").

## 지표

- `analyze`: `metrics.track("d-community-monitor", {stage:"analyze"})` → 성공 시 `generated`(소요 ms), LLM 응답이 JSON이 아니거나 필수 배열이 없으면 `failed`.
- `collect`: 소스 실패마다 `failed` (`meta.stage="collect"`, `meta.source`). 수집 성공은 생성물이 아니라서 기록하지 않는다.

## 테스트

`tests/d-community-monitor.test.ts` (네트워크 없음, fetcher 주입 + mock LLM): RSS 파싱(CDATA·엔티티·빠진 필드), 두 번 수집 시 중복 제거, 실패 소스(예외·HTML 응답)가 다른 소스를 막지 않음 + failed 지표, 토크나이저·불용어·조사 제거·글 수 집계, mock LLM으로 리포트·`readTopicHandoff` 확인, 근거 없는 항목 제거, JSON 오류 → failed 지표.

## 한계

- **뉴스는 사장님 목소리가 아니다.** 수집 글 대부분이 기업·지자체·교육기관 보도자료다.
- 키워드 상위권이 **검색어 자체**(소상공인, AI, 마케팅)와 **보도자료 복제 기사**(iM뱅크 제주 영업점 9건, 토스플레이스 쿠폰팩 9건)에 끌려간다. 제목이 조금씩 다른 같은 기사는 중복 제거로 못 거른다.
- 토크나이저는 형태소 분석 없이 조사만 떼는 수준이라 복합어·활용형이 갈라진다.
- 로컬 27B 모델로 67건 분석에 **259초**. 주 1회 배치면 괜찮지만 대화형으로 쓰기는 어렵다.
- Google 뉴스 링크는 `news.google.com/rss/articles/...` 중계 주소라 원문 URL이 아니다.

## 다음 단계

1. 사장님 목소리가 실제로 담긴 공개·허가 소스 확보: 네이버 검색 API(블로그·카페 **공개글** 검색 결과 제목·요약), 배민외식업광장·소상공인시장진흥공단 공지 RSS, 카페 제휴.
2. 검색어 단어를 키워드 집계에서 빼고, 제목 유사도(n-gram 자카드)로 보도자료 묶음을 1건으로 합치기.
3. 영업 포인트 프롬프트에 "타사 제품 홍보 금지, 우리 서비스가 풀 수 있는 고민만" 제약 추가.
4. `shared/handoff.ts`에 C용 `SalesAngleHandoff` 규약 추가 요청.

## Verdict: PARTIAL

실행 기록 (2026-11-23): `pnpm d:monitor collect` 2회 → 1회차 5개 소스 모두 성공, 새 글 67건(Google 뉴스 57 + 샘플 10), 수집 2.2초 / 2회차 새 글 0건(67건 모두 중복 처리). `pnpm d:monitor analyze --days 7` 1회(재시도 없음) → qwen3.8:27b **259.0초**, JSON 파싱 1번에 성공, 테마 4·고민 6·콘텐츠 아이디어 4·영업 포인트 4, 근거 없어 버린 항목 0. 상위 키워드: 소상공인(28), ai(23), 마케팅(11), im뱅크(9), 사장님(9), 제주(9), 토스플레이스(9), 영업점(7), 건양사이버대(6). 관심 키워드: AI 25, 마케팅 11, 쿠폰 10, 매출 4, 단골 3, 리뷰 3, 배달수수료 1, 인건비 1.

**What worked**
- 수집 → 중복 제거 → 코드 집계 → LLM 요약 → 리포트·A 전달까지 끝까지 돌았고, A가 `readTopicHandoff`로 바로 읽을 수 있는 주제 4개가 나왔다. 모든 주제에 실제 기사 링크가 붙어 있다.
- 근거를 글 번호로만 받는 방식이 잘 먹혔다. 지어낸 링크·제목이 없었고 모든 항목에 유효한 근거 번호가 있었다.
- 콘텐츠 아이디어 일부는 A에 쓸 만하다: "AI로 상세페이지·숏폼 직접 만들기", "AI 검색 시대 GEO 마케팅(챗GPT 가게 등록)", "지역 단골가게 사업 참여해 단골 만들기".

**What didn't**
- **사장님 고민(pain points) 6개가 전부 샘플 글에서만 나왔다.** 실제 뉴스 57건에는 사장님의 고민이 거의 없다(배달수수료 1건, 인건비 1건). 이 프로토타입의 핵심 목적인 "사장님 고민 찾기"는 공개 뉴스만으로는 달성되지 않았다.
- 영업 포인트 4개가 전부 **타사 제품 소개**(장사이지, WING-K, 소상공인365, 토스플레이스 쿠폰팩)였다. C가 그대로 쓰기 어렵다.
- 키워드 표 상위가 검색어와 보도자료 반복 기사에 지배돼 "트렌드" 신호로 보기 어렵다. 예: `자영업자 쿠폰` 검색 11건 중 9건이 iM뱅크 제주 지점 기사.

**Surprises**
- `when:7d`를 붙인 Google 뉴스 검색도 소스당 7~26건밖에 안 나와 30건 한도에 걸린 소스가 없었다.
- Google 뉴스 RSS 응답 자체에 비상업적 이용 한정 문구가 있었다. 상용으로 쓰려면 소스를 바꿔야 한다.
- 샘플 표시와 "실제 글을 우선 근거로" 지시가 있었는데도, LLM은 고민 항목에서 샘플을 근거로 썼다. 표시가 남아 있어서 걸러낼 수 있었다.

**Recommendation**
파이프라인(수집·중복 제거·근거 기반 요약·A 전달)은 재사용 가치가 있다. 다만 **소스가 바뀌기 전까지는 "사장님 고민 발굴" 용도로 쓰기 어렵고, "업계 뉴스 기반 A 글감 추천"으로만 쓰자.** 다음 투자는 모델이 아니라 소스다. 네이버 검색 API의 공개 카페·블로그 글이나 제휴 커뮤니티를 확보하고 보도자료 묶음 제거를 붙인 뒤 다시 평가하자. 비용은 주 1회 배치 기준 로컬 LLM 약 4~5분이면 충분하다.

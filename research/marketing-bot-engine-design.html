마케팅 봇 구축 설계 — 공용 엔진 + 서비스별 연결

작성 전준연 · 2026-11-23 · 1부 「쿠핀 PLUS 시장·생태계 분석」에 이어집니다
한눈에 보기
  • 사수님 방향 반영: 봇은 여러 서비스에서 함께 쓰므로 핵심 엔진은 하나로 만들고, 서비스마다 다른 부분은 연결부(어댑터)에서만 다룹니다. 첫 연결 대상은 쿠핀 PLUS(사장님)와 쿠핀 ON(소비자, B2C)입니다.
  • 엔진은 7단계로 동작합니다: 이벤트 수신 → 조건 판단 → 문구 생성(모델) → 검증 → 승인 → 발송 → 측정.
  • 모델 호출 원칙: 누구에게, 언제 보낼지는 규칙과 데이터가 정합니다. 모델은 조건을 통과한 경우에만 호출되고, 무엇을 어떻게 말할지(문구·요약·제안)만 맡습니다.
  • 마케팅 시나리오(플레이북)는 코드가 아니라 설정으로 추가합니다. PLUS 7개, ON 4개 후보를 정의했고, 이 중 3개를 먼저 병렬로 실험할 것을 제안합니다.

1. 왜 "공용 엔진 + 연결부" 구조인가

구분서비스마다 같은 것 → 엔진서비스마다 다른 것 → 연결부(어댑터)
무엇이 해당하나조건 판단, 모델 호출, 문구 검증, 승인 대기열, 발송 기록, 성과 측정어떤 이벤트가 오는지, 고객 데이터 조회, 수신 동의 확인, 발송 채널, 브랜드 톤
PLUS 예같은 코드 한 벌사장님 가입·구독·발송 이벤트, 콘솔 알림·알림톡
ON 예회원가입·구매·쿠폰 만료 이벤트, 앱 푸시·문자
이렇게 나누는 이유 설계 판단
① 유지보수: 검증 규칙이나 모델을 바꿀 때 엔진 한 곳만 고치면 모든 서비스에 반영됩니다. ② 확장: 새 서비스는 연결부만 만들면 되므로, PLUS·ON 다음에 CIMS나 회사의 다른 B2B 서비스를 붙이기 쉽습니다. ③ 병렬 실험: 시나리오를 설정 단위로 만들기 때문에, 사수님 방향대로 여러 방식을 동시에 돌리고 같은 기준으로 비교할 수 있습니다.

2. 엔진 구조

① 이벤트 수신→② 조건 판단→③ 문구 생성(모델)→④ 검증→⑤ 승인→⑥ 발송→⑦ 측정
단계하는 일모델 사용기존 코드에서 가져올 것
① 이벤트 수신서비스에서 온 신호를 공통 형식으로 바꿈. 신호 종류는 실시간(웹훅: 가입, 결제, 신규 상품), 예약(매시간·매일·매월 점검), 수동(운영자 실행) 세 가지없음handoff.ts(D→A 전달)
② 조건 판단시나리오별 조건을 확인: 수신 동의, 같은 사람에게 보낸 횟수 한도, 발송 가능 시간, 데이터 최소량. 여기서 걸러지면 모델을 부르지 않음없음B의 동의 분기 로직
③ 문구 생성시나리오에 연결된 프롬프트로 모델 호출. 결과는 정해진 JSON 형식으로만 받음사용llm.ts(json 옵션), prompts.ts
④ 검증빈칸 표시(OO, [이름]), 한자 섞임, 근거 없는 수치·과장 표현, 금지어, 길이, "(광고)" 표기 확인. 실패하면 1회 재생성 후 사람 검토로 넘김없음text.ts, A·D 검증 규칙
⑤ 승인시나리오마다 정한 승인 수준(아래 4장)에 따라 자동 통과 또는 대기열에 넣음없음approval.ts
⑥ 발송연결부의 채널로 보냄. 개발·실험 중에는 실제로 보내지 않음(DRY_RUN)없음channel.ts
⑦ 측정발송 → 열람·클릭 → 전환(가입, 쿠폰 사용 등)을 시나리오별로 기록. 같은 기준으로 비교없음metrics.ts, report-cli.ts

7단계 중 모델을 쓰는 곳은 ③ 하나입니다. 나머지는 일반 코드라 결과가 매번 같고, 테스트로 검증할 수 있습니다.

2-1. 엔진과 연결부 사이의 약속

이름담는 내용누가 만드나
이벤트서비스, 이벤트 종류, 대상(사장님·손님 ID), 발생 시각, 필요한 값연결부가 만들어 엔진에 넘김
플레이북
(마케팅 시나리오)		시작 신호, 조건, 사용할 프롬프트와 모델 등급, 검증 규칙, 승인 수준, 채널, 성공 지표설정 파일로 정의. 새 시나리오 = 설정 추가
연결부 기능대상 정보 조회, 수신 동의 확인, 발송, 승인 화면(어디서 누가 승인하나)서비스마다 한 번 구현
배울 점 설계 판단
엔진은 "PLUS"나 "ON"이라는 이름을 모릅니다. 연결부가 지켜야 할 약속만 알고 있습니다. 이렇게 하면 서비스 코드가 바뀌어도 엔진은 영향을 받지 않고, 엔진을 테스트할 때도 가짜 연결부만 있으면 됩니다. 지금 프로토타입의 MockLlmClient와 DryRunChannel이 같은 원리입니다.

3. 모델은 언제, 어떤 조건으로 호출되나

3-1. 쿠핀 PLUS 플레이북 (대상: 사장님)

플레이북언제 (시작 신호)어떤 조건이면모델이 하는 일승인
P1 가입 이어하기매시간 점검: 인증메일을 보낸 지 24시간이 지났는데 가입 완료가 없음안내 메일 수신 가능, 최근 7일 안내 0건멈춘 단계(서류·사업자번호 등)에 맞춘 안내 문구L1
P2 승인 대기 알림가입 신청 후 승인 대기 상태가 N시간 지남—호출 안 함. 운영자에게 알림만L0
P3 첫 쿠폰 도우미매일 점검: 구독 결제 후 72시간 동안 발송 0건상품 1개 이상 등록업종·상품 정보로 첫 쿠폰 이름과 메시지 3안 작성사장님이 고름
P4 리포트 → 실행월간 AI 리포트가 만들어질 때(매월 1일 또는 사장님이 열람할 때)동의한 손님 30명 이상, 이번 달 발송 한도가 남음리포트의 "다음 달 실행 과제"를 캠페인 초안(대상·시점·문구)으로 바꿈사장님 1클릭
P5 손님 다시 부르기매일 점검: 미사용 쿠폰, 60일 넘게 방문하지 않은 손님손님 광고 수신 동의, 손님별 월 1회 한도매장별 문구를 한 번만 만들고 저장해 재사용. 손님별 차이는 이름·쿠폰명 등 빈칸 채우기로 처리L1
P6 이탈 징후구독 갱신 7일 전최근 30일 발송 0건 또는 크레딧 미사용계정 상황 요약과 연락할 때 쓸 말을 운영팀에 전달(C 영업 브리프 재사용)L2
P7 사장님 유입 콘텐츠주 1회: D가 커뮤니티·뉴스 주제 수집근거 기사 2건 이상인 주제만블로그·카페 글 초안(A 재사용). 1부의 "무료 도구와 다른 점"을 소재로 사용L2

P1은 인증메일 발송 기록이 남는지 확인이 필요합니다. 현재 PLUS 가입은 이메일 인증 → 사업자 서류 → 가입 요청 순서로 진행됩니다.[3] P4의 AI 리포트는 지금은 사장님이 열람할 때 만들어집니다(PLUS 코드 확인).

3-2. 쿠핀 ON 플레이북 (대상: 소비자, B2C)

플레이북언제어떤 조건이면모델이 하는 일승인
O1 만료 임박 안내매일: 쿠폰 만료 30·7·1일 전휴대폰 번호 등록호출 안 함. ON에 이미 고정 문구 문자 발송이 있으므로 엔진으로 옮겨 측정만 통일L0
O2 첫 구매 유도가입 3일 뒤 구매 0건마케팅 수신 동의추천 쿠폰은 쿼리로 고르고, 모델은 소개 문구만 작성L1
O3 새 동네 쿠폰PLUS에서 새 상품이 ON에 연동될 때(웹훅)마케팅·위치 동의, 손님별 주 1회 한도상품 설명을 짧은 알림 문구로 요약L1
O4 SNS 콘텐츠주 1회: 인기 쿠폰 집계상위 5개인스타그램·블로그 글 초안L2

ON에는 마케팅 수신 동의 저장(변경 이력 포함)과 만료 알림 발송이 이미 구현되어 있어, 연결부를 만들기 쉽습니다(coupin-plus 코드 확인).

PLUS와 ON이 서로 이어지는 지점 해석
O3은 PLUS 사장님이 올린 쿠폰을 ON 소비자에게 알리는 플레이북입니다. 사장님 입장에서는 "PLUS를 쓰면 새 손님이 온다"는 근거가 되고, 1부에서 정리한 PLUS의 차별점(외부 판매 채널)을 실제 숫자로 보여 줄 수 있습니다.

3-3. 모델 호출 규칙 (모든 플레이북 공통)

항목규칙
모델 등급기본: 로컬 모델(현재 gpt-oss:20b). 배치·초안 작성용이고 비용이 들지 않음. 상위: 사장님이 화면에서 기다리는 실시간 작업(P3·P4)에만 상용 모델 사용. PLUS가 이미 쓰는 Gemini 계정을 재사용할 수 있음(확인 필요)
출력 형식JSON 스키마로 강제. 파싱 실패 → 1회 재시도 → 실패하면 미리 준비한 고정 문구로 대체
캐시같은 매장·같은 시나리오 문구는 저장해 재사용(P5). 손님별로 모델을 부르지 않음
비용 한도서비스별 월 호출 횟수 상한. 초과하면 고정 문구로 전환하고 운영자에게 알림
사실 확인숫자는 프롬프트로 넘긴 값만 사용(PLUS AI 리포트와 같은 원칙). 검증 단계에서 입력에 없는 숫자를 걸러냄
기록호출마다 프롬프트 버전, 모델, 소요 시간, 검증 결과를 남김. 문제가 생기면 어떤 버전이 원인인지 추적

4. 승인 수준과 안전 장치

수준의미해당 플레이북
L0자동 발송. 고정 문구나 거래·안내성 메시지P2, O1
L1문구 틀을 사람이 한 번 승인하면 이후 자동. 틀이 바뀌면 다시 승인P1, P5, O2, O3
L2건마다 사람이 승인. 외부에 공개되는 글이나 영업 연락P6, P7, O4
사장님 선택사장님 화면에 초안을 보여 주고 사장님이 고르거나 수정P3, P4
지켜야 할 것
광고성 메시지는 받는 사람이 미리 명시적으로 동의해야 하고, 개인정보 수집 동의만으로는 부족합니다.[1] 위반하면 과태료가 1회 750만 원부터입니다.[2] 따라서 엔진은 ② 조건 판단에서 연결부의 동의 확인을 반드시 통과해야 다음 단계로 넘어가게 만듭니다. PLUS에서 손님에게 보내는 메시지(P5)는 사장님이 발송 주체라서, 동의 책임을 누가 지는지 법무 확인이 필요합니다. 야간 발송 같은 세부 규칙도 법무 확인 후 조건에 반영합니다. 커뮤니티에는 자동으로 글을 올리지 않습니다.

5. 만드는 순서

단계할 일끝났다고 볼 기준
1단계
1~2주		엔진 뼈대(이벤트·플레이북·연결부 약속) 작성, 기존 src/shared 이전, 가짜 연결부로 P3·P4·O2를 병렬 실험(DRY_RUN)세 플레이북이 같은 엔진으로 동작하고, 같은 지표로 비교표가 나옴
2단계PLUS 개발 서버에 연결(웹훅 + 읽기 전용 조회), 사장님 몇 명과 시범 운영실제 가입·발송 데이터로 P3·P4 전환율 측정
3단계ON 연결, O1 이전(측정 통일), 운영자용 승인·성과 화면두 서비스가 하나의 엔진과 하나의 대시보드를 씀

먼저 실험할 3개를 고른 이유입니다. P3·P4는 1부에서 찾은 PLUS의 약점(무료 도구가 많아 계속 쓸 이유가 약함)을 직접 다룹니다. O2는 B2C에서도 같은 엔진이 동작하는지 확인하는 용도입니다. 셋 다 PLUS·ON에 이미 있는 데이터로 시작할 수 있습니다.

5-1. 기존 프로토타입은 이렇게 옮깁니다

프로토타입엔진에서의 역할
A 콘텐츠P7·O4의 문구 생성과 검증 규칙
B 문의 후속P1의 바탕이 됨(동의 분기, 승인, 후속 발송)
C 영업 브리프P6의 운영팀 브리프
D 모니터링P7의 시작 신호(주제 수집). 모델 없이 수집하는 구조 그대로 유지

6. 사수님과 정할 것

  • 엔진 위치 제안: coupin-plus 안의 라이브러리보다 별도 서비스로 두고, 각 서비스와는 웹훅·API로만 주고받는 방식을 제안합니다. 여러 서비스에서 함께 쓰는 봇이라는 방향과 맞고, 서비스 배포와 엔진 배포가 서로 묶이지 않습니다. 대신 연결부 API를 서비스 쪽에 만들어야 합니다.
  • 상용 모델: PLUS가 쓰는 Gemini 계정을 엔진에서도 쓸 수 있는지, 월 비용 한도는 얼마인지
  • 메시지 비용: P5처럼 사장님 손님에게 보내는 메시지를 사장님 크레딧에서 차감할지
  • 법무: 사장님이 보내는 광고 메시지에서 동의 책임 주체, 야간 발송 규칙
